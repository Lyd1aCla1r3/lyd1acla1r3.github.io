Runtime Infrastructure

The preceding chapters covered Connectivity and Routing and Data Infrastructure for retrieval. This chapter shifts to the model layer itself: the engines that serve open-weight models, the platforms that customize them through fine-tuning, and the observability tools that trace and evaluate their outputs. A capstone section maps how all the supporting ecosystem components interconnect.

Model Serving Infrastructure

Commercial model APIs abstract away hardware provisioning: the provider manages GPU clusters and model weights, executes forward passes remotely, and streams generated tokens back over HTTPS.

Organizations deploy open-weight models on dedicated infrastructure when workloads require strict data residency, predictable high-volume unit economics, or custom fine-tuned weights. Self-hosted inference requires GPU servers and three model artifacts: the weights (multi-gigabyte tensor files storing trained parameters), the tokenizer (vocabulary tables mapping text substrings to integer token IDs), and the configuration file (a JSON specification defining layer count, hidden dimensions, attention heads, and context length).

Serving a model begins by loading parameter tensors from disk into high-bandwidth GPU memory (VRAM). Standard PyTorch execution translates high-level tensor operations into GPU compute kernels, reserving the remaining VRAM after static weight allocation for active user requests.

KV-Cache Memory Fragmentation and Paging

Available VRAM for concurrent requests is the primary production bottleneck. Autoregressive language models generate tokens sequentially, storing intermediate attention states in a Key-Value (KV) cache so prior tokens do not require recomputation at each step. Naive PyTorch serving scripts pre-allocate a contiguous VRAM buffer sized to the maximum supported context length for every active request. Short completions leave up to 80% of that reserved buffer unused, causing severe internal memory fragmentation. Concurrent request batching quickly exhausts VRAM under contiguous allocation.

Unbounded concurrency under contiguous allocation also triggers KV-cache starvation: active sequences consume all free VRAM blocks before any single sequence reaches its end-of-sequence token, deadlocking the server. Production serving engines eliminate internal fragmentation through virtualized block-level memory paging and prevent starvation via continuous batching and request preemption, exposing an OpenAI-compatible HTTP API.

vLLM

Maker: vLLM Team / UC Berkeley LMSYS Community
License: Open-source (Apache 2.0)

vLLM is the standard open-source engine for high-throughput multi-tenant model serving. Its foundational mechanism, PagedAttention, applies operating-system virtual memory paging to the KV cache. Rather than requiring a single contiguous VRAM allocation per request, PagedAttention partitions the KV cache into fixed-size physical token blocks mapped via a logical block table. New tokens allocate physical blocks on demand from a global free list and release them immediately upon sequence completion, eliminating internal fragmentation and maximizing batch concurrency. Under memory pressure, vLLM prevents KV-cache starvation through request preemption and CPU offloading, pausing lower-priority sequences and swapping their KV blocks over PCIe to host DRAM until active sequences finish.

For models exceeding a single GPU memory envelope, vLLM supports tensor parallelism (splitting individual layer weight matrices and attention heads across GPUs within a node via high-speed interconnects) and pipeline parallelism (assigning sequential layer ranges across multiple nodes while interleaving micro-batches to keep compute units saturated).

Latency and throughput optimizations include speculative decoding (using a compact draft model to propose multiple candidate tokens that the target model verifies in a single parallel forward pass, amortizing HBM weight-bandwidth costs) and automatic prefix caching (sharing read-only KV-cache blocks across requests that share identical system prompts). vLLM runs across NVIDIA CUDA, AMD ROCm, Intel Gaudi, and Google Cloud TPUs behind a drop-in OpenAI-compatible server.

Pricing: Free and open-source.

SGLang

Maker: LMSYS Organization / RadixArk
License: Open-source (Apache 2.0)

SGLang is a high-performance serving engine co-designed for multi-turn agent trajectories, tree-of-thought search, and structured generation. Its memory engine, RadixAttention, maintains KV-cache blocks in an LRU-evicted radix tree (compressed prefix trie) across completed requests. Incoming prompts that share a token prefix with prior turns or parallel agent branches reuse the cached KV subtree in O(prefix) lookup time, computing attention only for newly appended tokens.

For schema-constrained JSON or grammar output, SGLang implements compressed finite-state machine (FSM) constrained decoding. Rather than evaluating token masks one token at a time, the runtime pre-compiles JSON schemas into a jump-forward FSM that masks invalid vocabulary logits at branch points and emits deterministic multi-token syntax sequences in a single step without extra forward passes.

SGLang also provides a co-designed frontend Domain-Specific Language (DSL) that executes multi-step prompt control flow, parallel forks, and conditional loops directly inside the serving runtime, eliminating repeated client-server network round trips across multi-step agent loops. Hardware backends include NVIDIA GPUs, AMD ROCm, and Google Cloud TPUs.

Pricing: Free and open-source.

Ollama

Maker: Ollama Inc.
License: Open-source (MIT License)

Ollama optimizes for zero-configuration local deployment on developer workstations and edge hosts rather than multi-tenant cluster throughput. The Go runtime packages model registry distribution, hardware backend detection, and a bundled llama.cpp inference engine into a single native binary for macOS, Linux, and Windows.

Executing ollama run resolves an OCI-style model manifest, downloads quantized GGUF weight layers, and launches a local HTTP daemon with automatic acceleration across Apple Metal, NVIDIA CUDA, or AMD ROCm. Built-in lifecycle commands (ollama pull, ollama list, ollama rm) manage local disk storage, and declarative Modelfile specifications bundle base weights with custom system prompts, sampling parameters, and chat templates behind an OpenAI-compatible API.

To preserve workstation responsiveness and prevent out-of-memory faults on consumer hardware, Ollama defaults to conservative concurrency and sequential request queuing, making it suited for local development, coding agents, and air-gapped single-node deployments rather than high-concurrency cluster serving.

Pricing: Free and open-source.

llama.cpp

Maker: Georgi Gerganov / ggml-org
License: Open-source (MIT License)

llama.cpp is the foundational C/C++ tensor and inference engine built on the ggml library. Unlike high-level wrappers, standalone llama-server exposes direct command-line control over KV-cache quantization, continuous batching slots, speculative draft models, and hybrid CPU/GPU layer splitting, requiring manual model file management and flag tuning.

The project defines the GGUF binary file specification, which packages quantized parameter tensors, tokenizer vocabularies, and architecture hyperparameters into a single memory-mappable file. Its quantization pipeline uses calibration importance matrices (imatrix) to measure activation sensitivity per weight channel, preserving salient weights at higher bit widths while compressing less sensitive tensors down to 1.5-bit to 4-bit representations. Zero-dependency C/C++ compilation enables native execution across x86 AVX/AVX-512, ARM NEON, Apple Metal, NVIDIA CUDA, AMD HIP, Vulkan, and SYCL.

Pricing: Free and open-source.

The four serving engines divide between multi-tenant data-center throughput and portable single-node or edge execution.

Selecting a serving runtime depends on concurrency requirements and deployment hardware. Ollama serves individual developers and air-gapped workstations needing one-command model management. vLLM serves high-concurrency production APIs requiring PagedAttention throughput and multi-node tensor or pipeline parallelism. SGLang accelerates multi-turn agent loops and strict JSON schema generation where RadixAttention prefix reuse and compressed FSM decoding reduce latency. llama.cpp targets edge devices, CPU/GPU hybrid hosts, and C/C++ environments that prohibit Python or PyTorch runtime dependencies.

Fine-Tuning Platforms

Prompt engineering and Retrieval-Augmented Generation (RAG) resolve most application requirements without modifying model parameters. Specific production workloads expose the ceiling of in-context steering. A support automation pipeline required to emit a complex nested schema may violate structural constraints on edge-case inputs regardless of how thoroughly the system prompt specifies the rules. A clinical summarization assistant may drift from institutional phrasing across long contexts, or a 50-way ticket classifier may plateau below required accuracy targets while consuming thousands of prompt-example tokens on every call.

Fine-tuning updates model parameters via supervised or preference-based gradient descent on curated task examples, encoding target formatting, tone, and classification boundaries directly into the weights. Fine-tuning a compact model frequently matches or exceeds the task-specific accuracy of a frontier model while reducing inference latency and eliminating lengthy few-shot system prompts.

Selecting between RAG and fine-tuning depends on the failure mode. Deficits in dynamic factual knowledge (internal policies, live inventory, or post-cutoff documentation) require RAG because retrieved context updates immediately without retraining. Deficits in behavioral consistency (adherence to output structure, domain syntax, or specialized reasoning style) require fine-tuning because parameter updates reshape the output distribution. Production architectures frequently combine both: fine-tuned adapters enforce behavioral structure while RAG supplies live factual grounding.

Hugging Face TRL and PEFT

Maker: Hugging Face
License: Open-source (Apache 2.0)

TRL (Transformer Reinforcement Learning) and PEFT (Parameter-Efficient Fine-Tuning) form the foundational Python training stack in the open-source ecosystem. TRL provides standardized trainer loops for Supervised Fine-Tuning (SFTTrainer), Direct Preference Optimization (DPOTrainer), and reinforcement learning with verifiable rewards (GRPOTrainer / PPOTrainer).

PEFT resolves the VRAM bottleneck of full-parameter training through Low-Rank Adaptation (LoRA) and QLoRA. Rather than computing gradients and optimizer states for billions of frozen base weights, LoRA freezes the pre-trained weight matrices (optionally quantized to 4-bit NormalFloat in QLoRA) and injects pairs of trainable low-rank decomposition matrices alongside target linear layers. Updating less than 1% of total parameters reduces optimizer and gradient memory overhead by up to 95%, enabling single-GPU fine-tuning.

Pricing: Free and open-source libraries; compute costs depend on the underlying GPU infrastructure.

Unsloth

Maker: Unsloth AI
License: Open-source (Apache 2.0 core)

Standard PyTorch autograd execution during LoRA fine-tuning materializes large intermediate activation tensors in GPU high-bandwidth memory (HBM) and dispatches separate kernel launches for rotary embeddings, layer normalization, and cross-entropy loss, making memory-bandwidth traffic the primary training bottleneck.

Unsloth replaces standard Hugging Face forward and backward pass operations with custom OpenAI Triton GPU kernels and analytical manual autograd derivations. Fusing operations in GPU SRAM and computing gradients in-place without materializing full logit tensors accelerates training throughput by roughly 2x and reduces peak VRAM usage by 60% to 80% with zero approximation loss. Trained adapters export directly to GGUF, vLLM, or Hugging Face Hub formats.

Pricing: The single-GPU open-source core is free under Apache 2.0, with commercial licensing for multi-GPU enterprise features.

Axolotl

Maker: OpenAccess AI Collective
License: Open-source (Apache 2.0)

Assembling an end-to-end distributed training pipeline from raw TRL, PEFT, and FlashAttention primitives requires extensive boilerplate code for dataset tokenization, chat-template masking, and multi-node process synchronization. Axolotl abstracts the entire training lifecycle behind a declarative YAML configuration specification.

A single YAML file declares the base checkpoint, dataset formats, LoRA or full-parameter hyperparameters, sample multipacking (concatenating short sequences into full context windows with attention masks to eliminate padding waste), and distributed scaling strategies via DeepSpeed ZeRO or PyTorch FSDP. Axolotl is the standard choice for reproducible, scriptless multi-GPU and multi-node cluster training.

Pricing: Free and open-source; organizations pay only for underlying GPU cluster compute.

OpenAI Fine-Tuning API and Managed Cloud Providers

Maker: OpenAI (proprietary); Together AI / Fireworks AI (open-weight managed cloud)
License: Proprietary SaaS

Managed fine-tuning platforms remove GPU cluster provisioning, driver maintenance, and distributed training configuration. Engineering teams upload a validated JSONL dataset of chat trajectories or preference pairs via REST API, and the platform schedules the training job and deploys the resulting adapter behind an autoscaled inference endpoint.

Closed-weight platforms (such as OpenAI Fine-Tuning) support Supervised Fine-Tuning, Direct Preference Optimization, and Reinforcement Fine-Tuning on proprietary models, trading infrastructure simplicity for vendor lock-in since trained weights cannot be exported. Managed open-weight platforms (such as Together AI) apply the same serverless training workflow to open-weight families (Llama, Qwen, DeepSeek) while allowing full download of the resulting LoRA adapters or merged checkpoints for self-hosted serving.

Pricing: Billed per training token processed plus per-token or hourly inference hosting rates.

Observability and Evaluation

Traditional application performance monitoring (APM) tracks HTTP status codes, system latency, and unhandled exceptions. Deterministic services passing those checks are healthy. Language model applications fail silently behind HTTP 200 responses: an agent loop can complete within latency budgets while hallucinating tool arguments, or a RAG retriever can return top-k chunks that lack the facts needed to answer the user query. Infrastructure metrics alone cannot detect semantic or reasoning failures.

Observability and evaluation address complementary halves of runtime quality assurance. Observability captures the complete execution trace of every request across nested spans, recording rendered prompts, model completions, tool payloads, retrieval scores, token counts, latency breakdowns, and cost. Evaluation measures output quality by scoring production or synthetic traces against reference datasets using deterministic assertions, human annotation queues, or LLM-as-judge rubrics. Production teams close the loop between both layers: observability surfaces failing production traces, dataset pipelines promote those failures into versioned regression suites, and automated evaluation gates verify that prompt or model updates resolve the failure without introducing regressions.

Langfuse

Maker: Langfuse GmbH
Focus: Full-lifecycle open-source observability and evaluation (MIT License)

Langfuse is an open-source LLM engineering platform covering hierarchical trace ingestion, prompt management, and evaluation. Traces model multi-turn conversations and agent loops as nested spans capturing input/output payloads, retrieval context, time-to-first-token latency, and per-step token cost.

Beyond tracing, Langfuse includes a version-controlled prompt registry with server-side caching, an interactive prompt playground, human annotation queues, LLM-as-judge scoring pipelines, and dataset curation directly from production spans. Native OpenTelemetry ingestion and export allow traces to flow alongside existing enterprise telemetry in Datadog or Splunk, with drop-in integrations for LangChain, LangGraph, LlamaIndex, LiteLLM, and DSPy.

Pricing: Free to self-host under the MIT License; managed cloud offers a generous free tier and tiered team or enterprise plans.

Braintrust

Maker: Braintrust Data, Inc.
Focus: Evaluation-driven CI/CD testing and proxy telemetry (proprietary SaaS, open-source SDKs)

Braintrust centers its architecture on evaluation-driven development and CI/CD regression gating. Engineering teams run parallelized offline and online evaluations against versioned datasets using deterministic code scorers, custom LLM-as-judge prompts, or the open-source autoevals library, comparing metric diffs across every pull request or prompt revision.

Production failing spans convert into regression test rows with one click. Braintrust also provides an integrated AI Proxy that caches responses, manages virtual keys, and captures request telemetry at the network layer without requiring application-level tracing SDK instrumentation. Native integrations cover LangChain, LangGraph, LlamaIndex, Instructor, and the Vercel AI SDK.

Pricing: Offers a free starter tier alongside flat-rate monthly team subscriptions and enterprise deployments.

Arize Phoenix

Maker: Arize AI
Focus: OpenTelemetry tracing and RAG embedding diagnostics (source-available, Elastic License 2.0)

Arize Phoenix combines vendor-neutral OpenTelemetry tracing with specialized vector embedding and retrieval diagnostics. Built on the open-source OpenInference semantic conventions for OpenTelemetry, Phoenix ingests traces from any instrumented framework without proprietary SDK lock-in.

Its UMAP point-cloud analyzer projects query and document embeddings into an interactive 3D manifold to surface low-performing retrieval clusters, query distribution drift, and corpus coverage gaps. Built-in evaluation templates score retrieval relevance, groundedness/hallucination, and Q&A correctness across LangChain, LangGraph, LlamaIndex, DSPy, Haystack, and CrewAI.

Pricing: Free for local and self-hosted container deployment; Arize AX / Phoenix Cloud provides managed tiers for teams and enterprises.

Weights and Biases Weave

Maker: Weights and Biases, Inc.
Focus: Application tracing with code and experiment lineage (Apache 2.0 SDK, proprietary platform)

Weave extends the Weights and Biases (W&B) experiment-tracking ecosystem from model training to generative AI application runtime monitoring. Decorating Python functions with @weave.op automatically instruments execution graphs, recording nested inputs, outputs, latency, token spend, and a content-addressed snapshot of the underlying function source code.

Organizations already tracking fine-tuning runs and model artifacts in W&B gain unified lineage from training checkpoints through application evaluation benchmarks. Weave evaluation pipelines version datasets and aggregate programmatic, human, and LLM-as-judge scores across model and prompt iterations, integrating natively with LangChain, LangGraph, LlamaIndex, DSPy, and Hugging Face.

Pricing: Free tier for individual developers and academic researchers, scaling to per-seat team plans and enterprise contracts.

How the Pieces Connect

Each supporting infrastructure zone integrates with coding agents, frameworks, and orchestrators at a defined architectural boundary:

  • Model Context Protocol (MCP): Standardized JSON-RPC servers connect coding agents, frameworks, and orchestrators to external tools and data sources, replacing bespoke per-vendor connectors with a unified tool and resource schema.
  • AI Gateways and Routers: Reverse-proxy gateways and semantic routers sit between agent execution runtimes and upstream model APIs, enforcing virtual-key multi-tenancy, budget caps, cross-provider failover, and prompt-complexity routing while exporting telemetry spans.
  • Vector Databases: High-dimensional ANN indexes store embedded document segments and execute hybrid dense-sparse and metadata-filtered retrieval whenever an agent or RAG pipeline queries for grounding context.
  • Knowledge Management Pipelines: Multimodal parsers, ETL connectors, and headless browser crawlers transform raw PDFs, enterprise wikis, and dynamic web applications into structure-aware Markdown and JSON chunks ready for embedding and vector indexing.
  • Model Serving Infrastructure: High-throughput GPU serving engines (vLLM, SGLang) and local inference runtimes (Ollama, llama.cpp) host open-weight and fine-tuned checkpoints behind OpenAI-compatible endpoints using paged or radix-tree KV-cache memory management.
  • Fine-Tuning Platforms: Parameter-efficient training libraries and declarative cluster orchestrators (TRL, PEFT, Unsloth, Axolotl) adapt base model weights on curated task datasets and export LoRA adapters or merged checkpoints directly into serving engines.
  • Observability and Evaluation Tools: OpenTelemetry dispatchers and callback hooks capture hierarchical execution spans from gateways, frameworks, and orchestrators, feeding production failure traces into automated evaluation datasets that gate prompt and model deployments.
